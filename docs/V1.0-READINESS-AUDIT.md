# Skattr v1.0 Readiness Audit

**Date:** 2026-06-12
**Scope:** Full-codebase architecture & functional review (all five crates + docs) against a v1.0 release bar.
**Method:** Eight parallel domain audits (crypto/protocol, delivery/mailbox, storage/daemon/IPC, UI/packaging, docs/threat-model, reliability/concurrency, spec-vs-code, security/crypto). The three highest-severity findings (T0-1, T0-3, T1-2) were independently re-verified by direct source inspection.

---

## Executive summary

The codebase is clean, well-tested at the unit/integration level, and faithful to its file-layout spec. **But it is not a working end-to-end messenger in its production wiring, and it is a long way from v1.0.** Three independent audits converged on the same structural finding, which I confirmed myself:

> **The daemon, as assembled in `Daemon::run`, can neither send nor receive a message between two real peers.** The direct peer-to-peer transport is never wired into the daemon (it exists and passes tests only via manually-driven `test_exports`), and the *only* inbound path that *is* wired — mailbox polling — fetches messages, deletes them from the server, and then discards them. A locked cryptographic binding the threat model depends on is also silently unimplemented.

The green test suite is real but misleading: the two-daemon flows pass because the tests hand-wire the Noise handshake and `hub.ingest()` themselves. Nothing does that in production.

### Verdict

**Not releasable as v1.0.** Not releasable as a functional messenger in current wiring. The work between here and a credible 1:1-messenger v1.0 is substantial (T0 + T1 below), and the project's own plan additionally gates a public 1.0 on a third-party security audit, attachments, and metadata-minimization defenses that do not yet exist.

## T0 — Showstoppers (the product does not perform its core function)

### T0-1. No production direct-message transport — onion is published but never accepted on, peers are never dialed  *(verified)*
`crates/core/src/daemon/state.rs:180-197`

`Daemon::run` calls `rt.publish_onion(...)` but **never** calls `TorRuntime::rend_requests_take()`, never constructs an `OnionListener`, and never calls `DeliveryHub::ingest()`. Verified by grep: `ingest`, `rend_requests_take`, `OnionListener::spawn`, `handshake_responder`, and `handshake_initiator` have **zero non-test call sites** in `crates/core/src`, `crates/cli`, `crates/ui`. The code even admits it at `state.rs:192-195`: *"injected via `hub.ingest()` from the onion-listener accept loop (wired in a later phase)."*

Consequences:
- **Inbound direct messages: impossible.** Rendezvous requests to the published onion are silently dropped; `handshake_responder` never runs.
- **Outbound direct delivery: impossible.** Peer actors are spawned cold (`conn: None`, `peer.rs:130-144`); the only way an actor gets a connection is `PeerCtrl::ReplaceConn` via `ingest()` — never called. Jobs immediately ack `Err(())` (`peer.rs:275-277`); `SendMessage` always returns `Queued` after the 2 s timeout and the outbox row is undeliverable by any mechanism.
- **Welcome propagation on `AddContact`: fails silently.** `send_welcome` enqueues to a conn-less actor whose ack `Err` is never awaited in `add_contact` — the inviter never joins the group.

**Fix:** wire the accept loop in `Daemon::run` (take the rend stream, spawn `OnionListener`, drive Noise on each `DataStream`, resolve X25519→Ed25519→ContactCard, and `ingest`), plus an outbound dialer that establishes the per-peer connection on first send. This is foundational, not incremental.

### T0-2. Mailbox polling destroys every fetched message  *(corroborated x2)*
`crates/core/src/mailbox/poll.rs:56-69, 431-452` + `crates/core/src/daemon/inbound.rs:68-79`

`run_one_poll_tick` fetches deposits **and server-side-deletes them** before returning (`poll.rs:63-68`). The actor then dispatches each ciphertext with `disp.dispatch(self_pk, &dep.ciphertext)` — passing **our own** pubkey as the sender (`poll.rs:448-451`, flagged as TODO Task 16/20). `DaemonInbound::dispatch_inner` resolves the group via `ContactRepo::get_group_id(&from)`; there is no contact row for our own pubkey, so it returns `Err("no group for peer")` → `dispatch` returns `None` → the result is discarded (`let _ = ...`).

**Net: every message fetched from a mailbox is deleted from the server and never persisted locally.** Since mailbox polling is the *only* inbound channel actually wired in production (given T0-1), the daemon has **no working inbound message path at all**.

**Fix:** decrypt-then-attribute (resolve the sender from the MLS sender identity rather than passing a peer in), and delete-after-successful-dispatch (not delete-in-tick) so a failed decrypt is retried on the next poll instead of losing the ciphertext.

### T0-3. IPC-reachable panic aborts the daemon  *(verified)*
`crates/core/src/daemon/dispatch.rs:364-434` → `crates/core/src/storage/messages.rs:122`

`Command::SendMessage { kind }` deserializes `kind` as the full `envelope::Kind` enum — including `ContactCardUpdate`, which is fully constructible over the wire. `send_message` performs **no kind validation**; it encrypts the envelope, then `insert_in_tx` hits `unreachable!("ContactCardUpdate is intercepted in DaemonInbound; never reaches MessageRepo")`. That comment is true only for the *inbound* path; the *outbound* path was overlooked. The panic fires **inside `pool.transaction` while holding the connection mutex**:
- **Release builds:** `[profile.release] panic = "abort"` (`Cargo.toml:138`) → the entire daemon process aborts.
- **Dev builds:** the pool mutex is poisoned → every subsequent storage call fails until restart.

Any local IPC client (the UI itself, the CLI, or a buggy script under the same user) can trigger this.

**Fix:** reject non-user-sendable `Kind` variants in `send_message` with `DaemonErrorKind::InvalidArgument`.

## T1 — Critical (security & data-integrity)

### T1-1. The `h_transport` transport↔MLS binding is derived but never injected into MLS  *(corroborated x3)*
`crates/core/src/transport/noise.rs:269` (derived) → never consumed; `crates/core/src/mls/group.rs:479-491` (only the invite PSK is registered)

CLAUDE.md lists this as a **locked technical decision**; design §1.5, `PROTOCOL.md`, `ARCHITECTURE.md`, and `THREAT_MODEL.md` all state `h_transport = HKDF(noise_handshake_hash, "skattr-binding-v1")` is "injected as an external PSK into the first MLS Commit" to prevent MLS-state replay / unknown-key-share across Noise sessions. In reality `h_transport` is computed, stored on the connection, and **used by no MLS code path**. The only PSK mixed into the group is the *invite PSK* — which is registered under the OpenMLS PSK id `b"skattr-binding-v1"`, reusing the binding's label and making a label grep falsely suggest the binding exists. The two layers are cryptographically independent; the defense the docs claim is absent. Not marked deferred anywhere — this reads as an oversight.

**Fix:** thread `AuthenticatedConnection::h_transport()` into the first Commit's external PSK, or file an ADR downgrading the claim and strike the binding language from design/PROTOCOL/THREAT_MODEL before any release that repeats it.

### T1-2. At-rest DB encryption is non-functional — plaintext SQLite persists; `.age` file never produced  *(verified)*
`crates/core/src/storage/pool.rs:119-132` + `crates/core/src/daemon/state.rs:137, 309-322`

`Pool::close(self)` is the *only* path that re-encrypts `skattr.sqlite` → `skattr.sqlite.age` and removes the plaintext. It consumes `self`, but the daemon shares the pool as `Arc` across hub/handle/sweep/scheduler/inbound and never reclaims it; the shutdown sequence never calls `close()`, and `Pool` has no `Drop`. Verified by grep: `close()`/`encrypt_db()` have no production callers. Consequences:
- Plaintext `skattr.sqlite` (+ WAL/SHM) — message bodies, MLS ratchet state, contacts — persists on disk after **every** shutdown, graceful or not.
- On a fresh install, `Pool::open` creates plaintext directly; `skattr.sqlite.age` is **never created at all**.
- `export_backup` requires `skattr.sqlite.age` to exist (`storage/backup.rs:36-49`) → **backup export always fails** on a daemon-managed data dir.

This nullifies the core at-rest-confidentiality property in the threat model and ADR 0003. The `pool.rs:24` comment ("Phase 1 should add a sync-on-checkpoint path") flags it as known debt that was never paid — and the reality is worse than the comment implies (no encryption ever, not merely a wider window).

**Fix:** give `Pool` a `Drop` that re-encrypts + unlinks (it already holds the derived passphrase), or have `Daemon::run` keep a non-`Arc` owner and `close()` after subsystem Arcs drop. Add a lock sentinel + re-encrypt-on-boot to handle crash residue.

### T1-3. Concurrent send causes an MLS ratchet race → "sent" messages the peer cannot decrypt  *(reliability audit)*
`crates/core/src/daemon/dispatch.rs:422-436` (no cross-load lock)

The IPC server spawns one task per connection (`ipc/server/mod.rs:187`). Two `SendMessage` commands for the same contact (UI + CLI, or two rapid UI sends on separate connections) run concurrently: both `Group::load` the same snapshot, both `group.encrypt` at the same MLS sender-ratchet generation (key/nonce reuse at the MLS layer), both `save_in_tx`. The `Mutex<Connection>` serializes only the SQL, not load→encrypt→save. Result: last-writer-wins ratchet; the receiver decrypts one ciphertext and rejects the other as a generation replay → a message marked sent locally is undecryptable by the peer. The same race exists three-way among `send_message`, `publish_self_card_update`, and `DaemonInbound::dispatch_for_group` (inbound also does load-decrypt-save on the same group).

**Fix:** a `tokio::Mutex` keyed by `group_id` around the load→encrypt/decrypt→save critical section.

### T1-4. `RemoveMailbox` final-drain permanently destroys held offline messages  *(Task 22.5)*
`crates/core/src/daemon/dispatch.rs:1109-1118`

`run_one_poll_tick` fetches and immediately server-side-deletes every pending deposit, and the handler discards the response (`let _ = ...`). Any messages waiting in a mailbox at removal time are permanently destroyed — never decrypted, never persisted, never surfaced. Triggered by a normal settings action (removing/rotating a mailbox). Silent, unrecoverable loss.

**Fix:** dispatch the drained deposits through `DaemonInbound` before finalizing, or use fetch-without-delete and let the normal poll path consume them.

### T1-5. Mailbox server abuse surface (anonymous, over Tor)  *(corroborated x2)*
`crates/mailbox/src/{dispatch,store,arti,server,policy}.rs`

For a semi-trusted/hostile deployment the server lacks several bounds:
- **No global storage cap** (`store.rs`, `policy.rs:25`): eviction is per-recipient only (256 MiB default). `recipient_hash` is attacker-chosen and deposits are unauthenticated by design → unlimited fresh recipient hashes each filled to the cap = unbounded disk (the committed soak summary shows monotonic growth). Disk-exhaustion DoS by an unauthenticated remote.
- **Cap-hit eviction only frees expired rows** (`store.rs:94-111, 220-249`): when nothing is expired, the insert is rejected → an attacker filling a victim's quota with non-expired deposits locks the victim out for the TTL (default 7 days). Targeted DoS.
- **No idle-connection timeout** (`server.rs:77`): `framed.next().await` blocks forever; idle circuits exhaust fds.
- **Unbounded per-stream `tokio::spawn`** (`arti.rs:139-174`): no semaphore/backpressure.
- **Per-circuit rate-limit reset** (`server.rs:67-72`): each new stream gets a fresh full deposit bucket; N circuits → N× the per-conn rate before the global bucket bites.
- **Unbounded `Delete.deposit_ids`** (`protocol.rs:148`, `store.rs:166-189`): one authed Delete with ~1M ids forces ~1M DELETEs under the store mutex.

**Fix:** add `max_total_storage_bytes` + recipient-count cap; LRU-fallback eviction (or require auth/PoW for deposit); idle timeout; connection semaphore; cap `deposit_ids.len()`; check global bucket before per-conn.

### T1-6. Direct→mailbox fallback is dead code  *(Task 20.5)*
`crates/core/src/delivery/hub.rs:312-462`, `peer.rs:233-237`, `state.rs:196-197`

`Daemon::run` builds the hub with `new_with_inbound` → `fallback: None`, so `ensure_mailbox_fallback` is a logged no-op. Even ignoring that, it has **zero production callers** (Task 20.5: the per-peer direct-timeout trigger that should fire it is unwired). And the retarget path is broken regardless: `set_mailbox_target` flips `target_kind` but leaves `target = peer` (`storage/outbox.rs:353-370`), `row_to_entry` discards `target_kind` (`delivery/outbox.rs:88-100`), and **no mailbox-deposit retry loop exists** — so a mailbox-kind row is retried over the *direct* channel (T0-1: which doesn't work) and never re-deposited.

**Net: the entire offline-delivery-via-fallback feature — the reason the mailbox subsystem exists — never executes in production.** Note this currently *masks* the broken all-fail retarget path; fixing the trigger will expose it, so they must be fixed together.

## T2 — Important

### T2-1. Invite single-use enforcement has a TOCTOU race
`crates/core/src/daemon/dispatch.rs:298, 332` — `is_consumed()` is checked at :298 and `mark_consumed()` only at :332, with MLS group-create + multiple separate-transaction writes in between. Concurrent/retried submission of the same invite (or a crash before :332) both pass the gate and create two groups, defeating the single-use invariant. Contrast the inbound path (`inbound.rs:320-321`) which correctly consumes in one tx. **Fix:** wrap check-and-consume in one transaction.

### T2-2. MLS `decrypt` gates on `can_send()` and errors on inbound Commits
`crates/core/src/mls/group.rs:240, 274-278` — receiving shouldn't require send capability; more importantly an epoch-change Commit arriving on the decrypt path returns an error instead of being merged, so the receiver doesn't ACK and the sender retries forever. Reachable once `advance_epoch` (PCS, already shipped) runs. **Fix:** split read vs send predicates; dispatch `StagedCommitMessage` to merge.

### T2-3. CI does not run the frontend test suites, nor build/validate Flatpak
`.github/workflows/ci.yml` (`ui` job) runs `pnpm build` + clippy + `cargo test` only — no Vitest, no Playwright. The 16 + 4 specs the project cites as its UI-correctness evidence don't gate merges. `release.yml` builds `.deb`/AppImage/`.dmg`/`.msi` but not the Flatpak that the docs advertise. **Fix:** add `pnpm test` / `pnpm test:e2e` (TAURI_MOCK=1) / `pnpm check` to the `ui` job; build or downgrade the Flatpak claim.

### T2-4. Download-verification chain is non-functional (placeholder keys + disabled updater)
`docs/install/minisign.pub` (all-zeros placeholder), `SECURITY.md` (PGP key "TBD"), `crates/ui/tauri.conf.json:64-67` (updater disabled). With the auto-updater off, minisign signature verification is the **only** supply-chain integrity path for manual downloads — and its key is a placeholder; `release.yml:288` would fail verification against a real keypair. The vuln-reporting PGP key is also a placeholder. **Fix (maintainer prerequisite):** generate + commit the real minisign and PGP keys, set CI secrets, remove placeholder language, and add a user-facing "updates are manual" section.

### T2-5. README is a full phase stale and claims unbuilt 50-member groups
`README.md` — status reads "Phase 1 almost complete"; lists shipped features (send, search, mailboxes, UI) under "What doesn't work yet"; line 23 promises "groups scale to ~50 members in v1" while code is hard-gated to 2 members (`mls/group.rs:97-99`) and the design scopes >2-member groups to Phase 3. False capability/security claims on the front page. **Fix:** rewrite to reflect Phase-2 completion and a 1:1-only v1.0.

### T2-6. Threat model is self-described "v0 / pre-audit" and under-states key metadata leaks
`docs/THREAT_MODEL.md:1-8` — bounds itself to "end of Phase 0," says it "will be revised before any public release." Specific gaps: (a) the recipient `identity-hash = SHA256(long-term pubkey)` is a **stable, non-rotating** cross-time correlator and two colluding mailboxes can confirm a shared recipient — A4 frames this only as "polling cadence"; (b) withhold-detection is *claimed* as a defense but no code compares consecutive `mls_generation` values or alerts (it's only latent in stored data); (c) onion rotation is sold as a privacy control but `RotateOnion` is degenerate (republishes the same onion, Task 23.5) and this is disclosed nowhere user-facing. **Fix:** revise to a v1.0 threat model covering the shipped UI/mailbox surface, with these three leaks stated plainly.

### T2-7. UI flattens the daemon's structured errors and silently loses live updates
- `crates/ui/src/ipc_bridge.rs:37` wraps every daemon error as `IpcError::Internal(String)`, discarding the `kind()` taxonomy Phase 1.H built.
- `crates/ui/src-svelte/.../AddContactDialog.svelte:41-44` collapses all add-contact failures (expired/consumed/bad-signature invite) to one opaque "Failed to add contact."
- `crates/ui/src/events.rs:38-45` breaks the relay loop on the first `Err` with no signal to SvelteKit → after a transient IPC hiccup all live updates (messages, delivery, Tor status) stop with a frozen-but-not-obviously-broken UI.

**Fix:** preserve structured `IpcError` to the frontend; render error kinds in the add flow; emit a terminal/error marker and re-subscribe on stream death.

### T2-8. MLS external PSK uses a fixed identity + zero nonce for every invite
`crates/core/src/mls/group.rs:479-486` — `PreSharedKeyId::external(b"skattr-binding-v1", vec![0u8;32])` is identical across all invites. OpenMLS keys PSKs on `(identity, nonce)`, so a second registration overwrites the first → with Phase-2+ multi-group support, the wrong PSK is retrieved at Welcome time (cross-group confusion / wrong-key binding). Masked today by single-group operation; overlaps with T1-1. **Fix:** derive a unique nonce/identity per invite (e.g. over the KeyPackageRef).

### T2-9. No GUI backup/restore; one-click wipe with no backup guard
`crates/cli/src/main.rs:69-89` (CLI-only backup) vs no UI path; `routes/settings/advanced/+page.svelte:182` (one-click irreversible "Delete all data and quit"). The primary (GUI) user can't back up without dropping to the CLI yet can wipe everything in one click. Realistic permanent data loss. **Fix:** add UI backup/restore, or gate the wipe behind a backup reminder and document the CLI procedure in first-run.

## T3 — Hardening & minor (defense-in-depth, polish, doc hygiene)

**Security hardening**
- `map_err` logs the full `CoreError` via `tracing::warn!(?err)` (`dispatch.rs:1304-1314`), bypassing the redactor (which only acts on formatted info+ text). Untrusted-input error text (malformed invite URLs with base64 key material, decrypt errors) lands in the ring buffer streamed to the UI via `TailLogs`. Log `err.kind()`/category only.
- HS-key age encryption uses `hex(HKDF(seed))` as the passphrase (`transport/hs_key.rs:56-83`) → deterministic ciphertext, no per-file salt; correlatable. Use XChaCha20-Poly1305 with a fresh nonce like `vault.rs`.
- Secrets serialized into non-zeroizing CBOR buffers (`identity/key.rs:116-135` `sign_cbor`/`verify_cbor` over bodies that include the invite PSK; `mls/key_package.rs:119-137` extra `.to_vec()` of the Ed25519 seed). Wrap in `Zeroizing`.
- `data_dir` created with default 0755 (`storage/pool.rs:48`); set 0700.
- `current_uid()` falls back `/proc/self` → `$UID` → `0` (`ipc/server/unix.rs:96-108`); on non-`/proc` Unix this is fragile. Use `libc::getuid()`.
- No per-command IPC authorization — any same-uid/SID process can `WipeAllData`. By-design single-user, but document it.
- `card.verify()` doesn't bound `expires_at` into the future — a card with `expires_at = i64::MAX` never expires. Clamp TTL on ingest.

**Reliability / correctness (minor)**
- Vault opened 4× at startup (`state.rs:130-134`) → 4× Argon2id KDF + four key copies. `Arc`-share one open.
- No schema-downgrade guard in the migration runner (`storage/migrations.rs`) — an older binary opening a newer DB silently "succeeds." Refuse if `current > max_known`.
- `seen_messages` 24h dedup sweep is hub-lifetime-bound; unbounded row growth during long downtime (replay safety is intact — it's in SQLite — but storage isn't bounded).
- `publish_self_card_update` hands card ciphertext to `hub.send` with no outbox row/retry (`dispatch.rs:1061`); with T0-1, every card update burns a ratchet advance and is lost.
- The Noise `psk_mismatch` test asserts only the responder and tolerates "stream closed" (`noise.rs:464-501`) — it doesn't prove no usable channel forms. Assert a failed post-handshake round-trip instead.
- `WipeAllData` uses a fixed 150 ms sleep to "let the reply flush" before exit (`dispatch.rs:1424-1444`) — fragile for an irreversible op; use a completion signal.

**Feature completeness (cut or disclose for v1.0)**
- **Attachments:** `Kind::File` exists but is never constructed; the entire `docs/skattr-attachments.md` spec (FileRef manifest, chunking, per-chunk keys, EXIF stripping) is unbuilt. Cut from v1.0 scope explicitly and hide any UI affordance.
- **Reactions / Edit / Delete / Typing:** `Kind` variants exist but are never sent and not handled — an inbound message of these kinds is silently persisted as an opaque history row (not applied). Decide reject-or-ignore; don't half-persist.
- **Groups > 2 members:** correctly deferred to Phase 3; the README claim (T2-5) is the only problem.
- **Onion rotation:** degenerate (T2-6); hide the control or disclose it does nothing yet.
- MLS state machine ships 3 of 6 designed states (`PendingCommit`/`CatchingUp`/`Removed` deferred); no out-of-order buffering. Acceptable for 1:1-online; document the constraint.

**Documentation drift**
- `ARCHITECTURE.md` (root) stale: says "migrations through 0006" (actually 14), "`mailbox::client` is `todo!()`" (fully implemented), socket name `daemon.sock` (now `ipc.sock`), pre-2.H IPC model.
- `docs/skattr-deep-dives.md` Part 3 describes a *different, non-shipped* mailbox protocol (HELLO/REGISTER/SUBSCRIBE, colliding type bytes) superseded by ADR 0006 but unmarked; its §1.2 documents the dead `Daemon::start/execute/shutdown` API instead of the real `Daemon::run`.
- `docs/skattr-deep-dives.md` §3.9 mailbox policy defaults diverge from code (rate ~30× more permissive, cap 256 vs 100 MiB, no count cap). `mailbox-setup.md` matches code; deep-dives is the stale one.
- `docs/PROTOCOL.md:31` wrong IANA codepoint (says 0x0001; code uses 0x0003). `docs/skattr-design.md` §1.5 still names the abandoned 256-bit AES suite.
- Dead `todo!()` stubs that contradict shipped behavior: `daemon/state.rs:44-66` (`Daemon::start/execute/shutdown`), `contact/rotation.rs:21-22` (`rotate_onion`).
- `docs/operations/passphrase-recovery.md` "Lost passphrase" tells users to delete `skattr.sqlite.age` — but the DB key is seed-derived (survives a passphrase reset), so this destroys recoverable history for no reason (and that file usually doesn't exist anyway — see T1-2). `docs/OPERATIONS.md:135-145` "re-encrypt by restarting cleanly" relies on the broken `Pool::close` path (T1-2) and is a no-op.
- **Missing ADRs** for the highest-stakes locked decisions (CLAUDE.md mandates ADRs for protocol changes): the Noise pattern, the `h_transport` MLS binding, the MLS ciphersuite, the `skattr://invite/v1` link format, and the envelope wire format. Only the mailbox protocol (0006) has one. Backfill before any external audit.

**`deny.toml` advisory ignores** — three of four Arti ignores (paste, rand+logger, rustls-webpki CRL) are genuinely unreachable as described; `RUSTSEC-2023-0071` (rsa Marvin) is defensible (Arti's rsa use is verify-only) but the comment should say *why* and carry a recheck date.

## What is solid (verified, no action)

- **Transaction atomicity on the persisted paths:** send (`dispatch.rs:422-436`) and receive (`inbound.rs:160-188`) each wrap MLS snapshot + message + outbox in one `pool.transaction`; the in-memory ratchet is only persisted on commit; a `Rejected` receive converts to `Err` *inside* the closure so the advanced ratchet rolls back. No path advances the on-disk ratchet without a durable row. (The *concurrency* gap T1-3 is orthogonal.)
- **IPC framing** is bounded — length validated against `MAX_IPC_BODY` before allocation; zero-length/oversize rejected. Same for the frame and mailbox codecs. Fuzz targets cover codec robustness.
- **Windows IPC FFI** (the one `unsafe` module) is sound — owner-SID-only DACL, `reject_remote_clients`, post-accept `EqualSid` defense-in-depth, every `unsafe` block SAFETY-commented, all handles closed on every path.
- **Unix peer-cred** uses kernel `SO_PEERCRED` (no TOCTOU); socket 0600, parent 0700, stale socket unlinked.
- **`verify_strict`** is used at the sole Ed25519 verify entry point; no malleability gap. `CoreError::kind()` is a pure structural match enforced by a guard test.
- **Crypto primitives & params** match spec: Argon2id m=64MiB/t=3/p=4, the locked ciphersuite 0x0003, replay window ±1h, dedup `(sender, message_id)`, domain-separated HKDF labels, `Zeroize`/`ZeroizeOnDrop` on all secret types, mailbox log-redaction enforced by a real test, 30 s single-use challenge nonces (sweep is wired in `mailbox/src/main.rs:70`).
- **UI/Tauri security:** CSP is tight (`script-src 'self'`, no `unsafe-eval`); all three `{@html}` sinks are static/backend-generated/escaped; all three Rust `eval()` sites are constant or JSON/whitelist-escaped; two-phase command surface enforced by a lint test; supply chain clean (pinned deps, no CDN, OFL/ISC assets bundled locally).
- **envelope_id backfill** is genuinely fail-closed; FTS triggers correct; migrations forward-only and transactional.

## Recommended path to v1.0

**Phase A — make it a working messenger (T0):** wire the inbound onion accept loop *with* known-contact validation + an outbound dialer (T0-1); fix mailbox-poll attribution + delete-after-dispatch (T0-2); validate `SendMessage` kinds (T0-3).
