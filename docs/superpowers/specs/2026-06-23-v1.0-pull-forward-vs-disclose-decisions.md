# v1.0 Pull-Forward vs. Disclose — Decision Record

**Date:** 2026-06-23
**Status:** Approved (brainstorm) — locks the loose-end disposition before Phase 4 scoping
**Purpose:** For every loose end carried out of Phases 1–3, record whether it is
**pulled forward into v1.0** or **disclosed as a v1.1 known limitation**. This list
is the authoritative input to Phase 4 — especially **4.B (documentation
truthfulness)**, whose `THREAT_MODEL.md` / README / first-run rewrites must
disclose exactly the items marked "disclose" here and no fewer.
**No code changes in this document.** It is a decision record; the pulled-forward
fixes are implemented inside their Phase 4 sub-projects.

---

## Governing bar

> **Cheap security/correctness fixes are pulled into v1.0; anything requiring real
> protocol or architecture work is disclosed as a v1.1 known limitation.**

"Cheap" = small, local, low-risk change with no wire-protocol/ADR impact. "Real
protocol/architecture work" = changes that touch the frozen ADR 0006 mailbox wire
protocol, MLS/handshake semantics, or introduce a new subsystem.

One item (first-contact `Welcome`) takes a deliberate middle path under this bar:
disclose the architectural gap, but add a **client-side-only** UX mitigation.

---

## Decisions

### Pull forward into v1.0

| # | Item | Fix | Cost | Phase 4 home |
|---|---|---|---|---|
| P1 | **Opener path confinement** (3.D follow-up M1): `open_file` / `reveal_in_folder` validate canonicalize + regular-file but are not scoped to the downloads dir | Thread the download dir in; reject paths not under `<data_dir>/downloads` (`canon.starts_with(&downloads)`) | Small, local validation | 4.D (T3 hardening) |
| P2 | **3.C completion atomicity**: the attachment-complete check is not atomic with the status flip; simultaneous direct (3.B `finalize_rx`) + offline (3.C `finalize_offline`) completion can double-fire `AttachmentReceived` | Compare-and-set status gate — `UPDATE … SET status='complete' WHERE status='pending'`, use rows-affected as the single fire gate | One query, no schema change | 4.D (attachment hardening) |
| P3 | **3.C swallowed logs**: `chunk_sweep` prune writes and `finalize_offline` post-reassemble status writes are dropped with `let _ =` | Add `warn!` on failure | Trivial observability | 4.D |
| P4 | **Indeterminate-progress test** (3.D follow-up M2): the `FileAttachmentBubble` ≤8-chunk "Downloading…" (indeterminate) branch has no unit test | Add one Vitest case (`applyProgress` with `total === 0` → indeterminate render) | One test | 4.A (CI/test) |
| P5 | **`PromotedMessage` cast cleanup** (3.D follow-up M3): `sendFile` promotion uses `{ …, __optimistic: false } as unknown as OptimisticMessage` (type-unsound — the brand requires `__optimistic: true`) | Introduce a small `PromotedMessage` type, or drop the optimistic brand fields on promotion | Cosmetic | Any convenient Phase 4 PR |

**Rationale notes:**
- **P1** makes the opener commands *safe-by-construction* rather than
  *safe-by-context*. Today they are only safe because their path argument is always
  daemon-authored (from `Event::AttachmentReceived`) and the webview is locked by
  `script-src 'self'`. The confinement defends against a future regression that wires
  a user-supplied path into these commands. It belongs naturally in Phase 4's T3
  hardening cluster.
- **P2** user-visible harm today is near-nil (the UI store keys on `attachment_id`
  and re-applies the same complete state idempotently), but a duplicate
  `AttachmentReceived` can still drive a duplicate desktop notification. The CAS gate
  removes the wart at the source for one query's cost.

### Disclose as v1.1 known limitation

| # | Item | Why deferred | Disclosure surface |
|---|---|---|---|
| D1 | **First-contact `Welcome` is direct-only** — if the inviter is offline when the joiner sends the Welcome, first contact stalls (old Task 2.E.5). Ordinary messages + ContactCard updates *do* have mailbox fallback (2.C); the Welcome frame does not. | Routing Welcome through the mailbox is protocol work that extends the ADR-0006 freeze | first-run UX + `THREAT_MODEL.md` + README — **plus the D1 mitigation below** |
| D2 | **Degenerate onion rotation** (Task 23.5) — `Command::RotateOnion` bumps the self-card version and republishes the *current* onion; contacts see a new `ContactCardReceived` version but route to the same address | Real onion-key rotation is significant key-management work | `THREAT_MODEL.md` (roadmap already plans this disclosure) |
| D3 | **3.C offline transfer is best-effort** — a deposited-but-never-fetched attachment is lost after the mailbox TTL (~7 days; the sender gets no fetch feedback so it never re-deposits); a stalled inbound stays `pending` forever (no auto-fail / partial-GC janitor); files > 10 MiB cannot transfer while a peer is offline | Needs a new fetch-feedback + re-deposit + partial-GC subsystem | `THREAT_MODEL.md` + README (attachment limitations) |

#### D1 mitigation (pulled forward; client-side only)

Ship the first-contact gap **disclosed**, but soften the failure mode with a
**client-side-only** improvement — no wire-protocol change, no ADR:

1. **In-UI "waiting for contact" state** — when the joiner has added a contact but
   the Welcome has not yet been delivered, surface an explicit "Waiting to connect —
   your contact must be online" state instead of a silent stall.
2. **Joiner-side auto-retry** — the joiner periodically re-dials and re-sends the
   *same* Welcome frame until it succeeds, so first contact **self-heals** when the
   inviter comes online.

**Hard guardrail:** this mitigation MUST remain client-side and protocol-neutral.
If, during 4.C planning, the auto-retry turns out to require any change to the
wire protocol, the mailbox path, or persisted cross-peer state beyond what the
joiner already retains, **drop the auto-retry and ship pure disclosure (the in-UI
waiting state alone is still acceptable).** Do not extend the ADR-0006 freeze for
this.

### Already decided — confirmed disclose (not re-litigated)

The standing v1.1+ deferral list remains disclosed-as-absent in the v1.0 threat
model; these were settled in the v1.0 roadmap and are listed here only so 4.B has
the complete disclosure set in one place:

- Third-party security audit
- Metadata-minimization: message-size padding, send-timing jitter, cover traffic /
  cover polling
- Multi-member groups (> 2)
- Reactions / edit / delete-for-everyone / typing / read receipts (the `Kind`
  placeholders stay inert)
- Multi-device
- The stable-recipient-hash mailbox-correlation leak (roadmap T2-6)

## Implications for Phase 4 scoping

This record does **not** change the Phase 4 decomposition; it populates it:

- **4.A — Release integrity & CI:** absorbs **P4** (indeterminate-progress test)
  alongside the existing CI-completeness work (Playwright + `pnpm check` in the `ui`
  job, Flatpak).
- **4.B — Documentation truthfulness:** the `THREAT_MODEL.md` / README / first-run
  rewrites disclose exactly **D1, D2, D3** + the already-decided list above, and
  cite this record. No new engineering — pure docs.
- **4.C — UI robustness & data-safety UX:** absorbs the **D1 client-side
  mitigation** (waiting state + joiner auto-retry) alongside the planned structured
  daemon-error surfacing, stream-death signal, and backup-before-wipe work.
- **4.D — T3 hardening:** absorbs **P1** (opener confinement), **P2** (3.C
  atomicity CAS gate), **P3** (warn logs), and **P5** (cast cleanup) alongside the
  roadmap's cluster-6 hardening items.

**Net new scope created by this record:** only the D1 client-side mitigation
(modest, UI-side, 4.C). Everything else either rides existing Phase 4 clusters
(P1–P5) or is pure documentation (D1–D3 disclosure).

## Disclosure language seeds (for 4.B to lift)

Ready-to-edit phrasing so the threat-model rewrite starts from agreed wording:

- **First contact (D1):** "Establishing first contact requires both peers to be
  online at the same time. If your contact is offline when you add them, the
  connection is retried automatically and completes once they come back online; it
  will not complete until then."
- **Onion rotation (D2):** "The 'rotate onion address' action re-publishes your
  current address with a new card version; it does not yet generate a new onion
  address. True address rotation is planned for a later release."
- **Offline attachments (D3):** "Attachments sent while your contact is offline are
  held by a mailbox for up to ~7 days and delivered when they reconnect. Delivery is
  best-effort: an attachment never fetched within that window is dropped, and files
  larger than 10 MiB are only delivered while both peers are online. Text messages
  are not subject to these limits."
