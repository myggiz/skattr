# Skattr v1.0 Release Roadmap

**Date:** 2026-06-12
**Status:** Approved scope; per-phase specs to follow.
**Source:** `docs/V1.0-READINESS-AUDIT.md` (eight-domain audit, 2026-06-12).

This roadmap defines the phases required to take Skattr from its current
end-of-Phase-2 state to a credible, shippable **v1.0**. It is a planning
document, not an implementation plan. Each phase below gets its own
`spec → plan → implement → verify` cycle; this roadmap fixes the scope,
sequencing, and exit criteria so those cycles stay focused.

---

## 1. Scope (locked)

**v1.0 is a 1:1 (2-member) metadata-resistant encrypted messenger with file
attachments, over Tor v3 onion services, using direct peer-to-peer transport
with a mailbox-based offline-delivery fallback.**

### In scope
- Working direct P2P message send/receive between two real daemons.
- Mailbox-based offline delivery as a fallback when a peer is unreachable.
- File attachments (send, receive, preview) with metadata stripping.
- All T0 (functional) and T1 (critical security/data-integrity) audit fixes.
- Honest, accurate user-facing documentation and a working download-verification chain.

### Out of v1.0 scope (→ v1.1 fast-follow)
These are explicitly deferred and **must be disclosed as absent** in the v1.0
threat model so users do not over-trust:
- **Third-party security audit.**
- **Metadata-minimization defenses:** message-size padding, send-timing jitter, cover traffic / cover polling.
- **Multi-member groups (>2):** the full MLS multi-member state machine, add/remove/leave, fanout delivery.
- **Real onion-key rotation** (current `RotateOnion` only bumps the ContactCard version — Task 23.5).
- Reactions, message edit, delete-for-everyone, typing indicators, read receipts (the `Kind` placeholders stay non-functional and are either rejected or explicitly inert).
- Multi-device.

### Non-goals (permanent, per existing threat model)
Server-side message storage beyond offline mailboxes; recovery of a lost
seed phrase; protection of a fully compromised endpoint.

---

## 2. Cross-cutting principle: the regression guardrail

The audit's defining finding was **"green tests, dead production path"** — the
two-daemon flows pass only because tests hand-wire the transport via
`test_exports`; nothing wires it in `Daemon::run`. Every phase below must
therefore add or extend an **integration test that exercises the real
`Daemon::run` assembly end-to-end** (two daemons over loopback / in-process
transport, *not* `test_exports`). No phase is "done" until its behavior is
proven through the production wiring, not a test harness that bypasses it.

This guardrail is introduced in Phase 1 and extended in every later phase.

---

## 3. Phases

Dependencies are strict: **Phase 1 → 2 → 3 → 4.** Phase 3 (attachments)
depends on Phase 2's hardened mailbox/transport; Phase 4 (docs/release) depends
on all behavior being frozen.

### Phase 1 — Make messaging work (T0) + guardrail

**Goal:** two real daemons exchange messages in both directions through the
production `Daemon::run` wiring, online and offline.

Work items (audit refs in brackets):
1. **Inbound onion accept loop** wired into `Daemon::run`: take the rendezvous
   stream from `publish_onion`, spawn the onion listener, run `handshake_responder`
   per `DataStream`, resolve `peer_x25519 → Ed25519 → ContactCard`, and **reject
   any unknown/unauthenticated peer before `DeliveryHub::ingest()`**. [T0-1 inbound + latent auth gap]
2. **Outbound dialer:** on first send to a peer with no live connection, dial the
   peer's onion via Arti, run `handshake_initiator`, and `ingest()` the
   connection so the per-peer actor can deliver. [T0-1 outbound]
3. **Fix mailbox-poll inbound:** decrypt-then-attribute the sender from the MLS
   sender identity (stop passing the self pubkey); **delete deposits only after a
   successful dispatch**, so a failed decrypt is retried on the next poll instead
   of destroying the ciphertext. [T0-2]
4. **Validate `SendMessage` kinds:** reject non-user-sendable variants
   (`ContactCardUpdate`, and any other internal kind) with
   `DaemonErrorKind::InvalidArgument` before encryption, eliminating the
   `unreachable!()` daemon-abort path. [T0-3]
5. **Guardrail test:** a `Daemon::run`-level integration test (two daemons,
   loopback transport) that drives invite → add → bidirectional send → receive
   and asserts delivery, both online (direct) and with one peer offline (mailbox).

**Exit criteria:** the guardrail test passes; a manual two-daemon run exchanges
messages both directions; sending an internal `Kind` returns a typed error
instead of crashing; mailbox-fetched messages are persisted and surfaced.

### Phase 2 — Critical security & data-integrity (T1 + security-critical T2)

**Goal:** the now-working flows are cryptographically and durably sound, and the
mailbox server is safe to expose to anonymous Tor traffic.

Work items:
1. **`h_transport` transport↔MLS binding:** inject `AuthenticatedConnection::h_transport()`
   as the external PSK into the first MLS Commit (the locked design), **or**
   formally retire the claim via an ADR and strike it from design/PROTOCOL/threat-model.
   Decide explicitly; do not leave it silently unimplemented. [T1-1]
2. **Real at-rest DB encryption:** ensure the daemon re-encrypts `skattr.sqlite`
   → `skattr.sqlite.age` and removes the plaintext on shutdown (via `Pool::Drop`
   or a reclaimed-owner `close()`), plus crash-residue handling — a lock sentinel
   and re-encrypt-on-boot if plaintext is found. Restore `export_backup`. [T1-2]
3. **Per-group send lock:** a `group_id`-keyed async mutex around the
   load→encrypt/decrypt→save critical section to eliminate the concurrent-ratchet
   race that produces undecryptable "sent" messages. [T1-3]
4. **`RemoveMailbox` drain fix:** dispatch drained deposits through `DaemonInbound`
   before finalizing removal (or fetch-without-delete and let the poll path consume
   them), so removing a mailbox doesn't destroy held offline messages. [T1-4]
5. **Wire & fix direct→mailbox fallback:** fire `ensure_mailbox_fallback` on
   sustained direct-delivery failure (Task 20.5), and fix the retarget/retry
   correctness — `target_kind` must be honored, mailbox-kind rows must be retried
   over the mailbox path (not the direct channel), and the row must only be
   retargeted on deposit success. [T1-6]
6. **Mailbox server resource hardening:** global storage cap + recipient-count cap,
   LRU-fallback eviction (so a fresh legitimate deposit can always land), idle-connection
   timeout, per-server connection bound/semaphore, and a bounded `Delete.deposit_ids`
   length. [T1-5]
7. **Per-invite PSK uniqueness:** derive a unique PSK nonce/identity per invite to
   prevent cross-invite PSK overwrite. [T2-8]
8. **Invite single-use atomicity:** wrap the check-and-consume (+ group/contact
   writes) in one transaction. [T2-1]
9. **Inbound-Commit handling:** split read vs send predicates in MLS `decrypt`;
   merge an inbound `StagedCommitMessage` instead of erroring, so PCS epoch
   advances don't stall delivery. [T2-2]

**Exit criteria:** the binding decision is made and reflected in code + docs;
plaintext DB is gone after a clean shutdown and recovered safely after a crash;
a concurrency test proves no ratchet race; mailbox removal preserves messages;
fallback fires and delivers offline; the mailbox server survives an
anonymous-flood and a targeted victim-fill without unbounded disk or lockout.

### Phase 3 — Attachments subsystem

**Goal:** users can send and receive files in a 1:1 conversation, with
attachment metadata stripped, over both the direct and offline paths.

Work items (to be detailed in the phase spec):
1. **Wire format:** `FileRef`/attachment-manifest types (chunk hashes, per-chunk
   keys, size, MIME), reusing the existing `Kind::File` placeholder.
2. **Chunker + per-chunk encryption:** split, encrypt per chunk, reassemble;
   integrity-verify on receive.
3. **Metadata stripping:** EXIF/metadata removal before send.
4. **Transport:** chunk transfer over the (now working) Noise/MLS channel; resume
   semantics for interrupted transfers.
5. **Offline path:** mailbox blob storage for attachment chunks (inheriting Phase 2's
   global caps), with size/TTL limits.
6. **UI:** attach/send, download/receive, inline preview, progress, and clear size limits.
7. **Guardrail:** extend the `Daemon::run` integration test to round-trip a file.

**Exit criteria:** a file round-trips between two daemons (direct and offline),
EXIF is stripped, oversize attachments are rejected with a clear error, and the
mailbox caps bound attachment storage.

### Phase 4 — Release integrity, UX & documentation truthfulness

**Goal:** the release is verifiable, the UI surfaces failures, and every doc
matches shipped behavior. Done last because docs can only be truthful once
behavior is frozen.

Work items:
1. **CI:** run the frontend test suites (Vitest + Playwright with `TAURI_MOCK=1`)
   and `pnpm check` in the `ui` job; build or validate the Flatpak in CI (or
   downgrade the docs to "community build-from-source"). [T2-3]
2. **Signing:** generate + commit the real minisign public key and PGP key, set the
   CI secrets, remove placeholder language; add a user-facing "updates are manual"
   section (the auto-updater is disabled). [T2-4]
3. **Documentation truthfulness:**
   - Rewrite `README.md` and `THREAT_MODEL.md` to the 1:1+attachments scope;
     disclose deferred metadata-minimization, the degenerate onion rotation, and the
     stable-recipient-hash mailbox-correlation leak. [T2-5, T2-6]
   - Fix `passphrase-recovery.md` (stop telling users to delete recoverable data)
     and `OPERATIONS.md` (the re-encrypt-on-restart remediation). [T1-2 follow-through]
   - Reconcile `ARCHITECTURE.md`, `skattr-deep-dives.md` (mailbox + MLS sections),
     and `PROTOCOL.md` with shipped behavior. [T3 docs]
   - Backfill missing ADRs: Noise pattern, MLS binding, ciphersuite, invite-link
     format, envelope wire format. [T3 docs]
4. **UI robustness:** surface structured daemon errors to the frontend (stop
   flattening to `Internal`), render error kinds in the add-contact flow, and emit a
   stream-death signal so the UI doesn't silently freeze on IPC hiccups. [T2-7]
5. **Data safety UX:** add GUI backup/restore, or gate the one-click wipe behind a
   backup reminder and document the CLI backup procedure in first-run. [T2-9]
6. **High-value T3 hardening:** fix the `map_err` log-redaction bypass; salt the
   HS-key encryption; create `data_dir` 0700; wrap secret CBOR buffers in
   `Zeroizing`; add a schema-downgrade guard; use `getuid` for the Unix uid fallback. [T3]

**Exit criteria:** a tagged build verifies against the published minisign key;
CI gates on frontend tests; README + threat model accurately describe v1.0;
the UI surfaces daemon errors and stream death; GUI users can back up before they
can wipe.

---

## 4. Sequencing and rationale

```
Phase 1 (functional)  ──►  Phase 2 (security/integrity)  ──►  Phase 3 (attachments)  ──►  Phase 4 (release/docs)
```

- **Phase 1 first:** nothing else is meaningful while messaging doesn't work in
  production; and the guardrail must exist before further change so regressions
  surface immediately.
- **Phase 2 before Phase 3:** harden the transport, MLS binding, at-rest storage,
  and mailbox caps *before* adding the attachment attack surface, so attachments
  inherit a hardened base.
- **Phase 3 before Phase 4:** attachments change the wire format, mailbox storage
  profile, and UI — docs can't be frozen until they're in.
- **Phase 4 last:** docs, threat model, signing, and release CI describe final behavior.
