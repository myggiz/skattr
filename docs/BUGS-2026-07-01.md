## Summary

| # | Bug | Severity | Status | Fix complexity |

transfer, large files never leave the sender.

## #1 — Attachments > ~15.6 MiB silently never send

**Symptom:** The two 20.4 MiB `.gif` files never appeared on the receiver — not even
the filename. No error on the sender.

**Root cause:** The manifest travels inside the MLS envelope as
`Kind::File { manifest: Vec<u8> }` at `crates/core/src/envelope/kinds.rs:27` —
**without `#[serde(with = "serde_bytes")]`**. So when the envelope is CBOR-encoded for
the wire, that byte vector is serialized as a *CBOR array of integers* (~1.9 bytes/byte),
nearly doubling it. The result is sent as a single `Frame::MlsApp`, and the transport
**hard-rejects** any frame over 65519 bytes with no fragmentation
(`crates/core/src/transport/connection.rs:88-99`). The rejection is then **silently
swallowed** in the actor (`crates/core/src/delivery/peer.rs:543` — `let _ = ...; continue`),
so nothing surfaces to the UI.

**Evidence (measured locally):**

| File | Chunks | Raw manifest | In envelope (`Vec<u8>`) | vs 65519 cap |
|------|--------|--------------|--------------------------|--------------|
| 6.3 MiB | 135 | 13.4 KB | **26.7 KB** | fits |
| 20.4 MiB | 436 | 43.1 KB | **85.5 KB** | exceeds |

Threshold: **fails above ~15.6 MiB**.

**Fix:** Add `#[serde(with = "serde_bytes")]` to the manifest field (drops the 20.4 MiB
envelope to ~43 KB — fits). **This is a wire-format change** (CBOR array → byte string):
both peers must upgrade together → needs an ADR / version note.

**Deeper limitation:** Even after that fix, files **> ~31 MiB** still fail, because the
raw manifest itself eventually exceeds the frame cap. The real fix is the *chunked send
path* the code comment admits was deferred (`connection.rs:91`), or paginating the
manifest. Note `serde_bytes` is already correctly used on the `Chunk` frame's ciphertext
(`transport/frame.rs:38`) — just missing on the manifest.

## #2 — Chunk transfer times out even when the manifest arrives

**Symptom:** The 6.3 MiB `.mp4` — the filename (manifest) arrived on the receiver, but
the file never did; the receiver reports "request timeout". Text messaging works fine in
both directions.

**Diagnosis so far:** The failure reason is diagnostic — "request timeout" (not "sender
nack reason N", not "chunk hash mismatch") means the receiver sent `ChunkRequest` frames
and the sender replied with **nothing at all**. Everything in the static path looks
correct: production wiring passes `chunk_store` + `download_dir` to every actor, the
sender has the `out` row and staged chunks, and the `Chunk` frame fits the cap. Since text
round-trips both ways, it's not a general connection problem — it's specific to the chunk
serve/pull path.

**Leading hypothesis:** connection **topology coverage gap**. The only integration test
(`crates/tests/src/attachment_transfer_direct.rs`) has the *receiver* initiate the
connection (via `add_contact`), so it pulls chunks over its own outbound conn. In
production the *sender* dials, and the receiver must pull back over a purely accepted /
`ReplaceConn`'d connection — a path with **zero test coverage**.

**Status:** Root cause not yet pinned. Recommended next step: a loopback integration test
that establishes the connection *sender-first*, then `SendFile`, to reproduce
deterministically without Tor.

**Relevant code:** serve arm `crates/core/src/delivery/peer.rs:786-815`; receiver state
machine `crates/core/src/delivery/chunk_transfer.rs`.

## #3 — Tray menu flashes; Quit unreachable

**Symptom:** Closing sends to tray (intended); right-clicking the tray icon shows a menu
that flashes away instantly, so **Quit can't be clicked**.

**Root cause:** `crates/ui/src/tray.rs:77-88` — `on_tray_icon_event` matches
`TrayIconEvent::Click { .. }`, i.e. **any** button. With `show_menu_on_left_click(false)`,
a right-click both (a) opens the context menu and (b) fires the handler, which toggles the
window and calls `w.set_focus()`. The focus change dismisses the just-opened menu.

**Fix:** Filter the handler to left-click release only:

```rust
use tauri::tray::{MouseButton, MouseButtonState};
if let TrayIconEvent::Click {
    button: MouseButton::Left,
    button_state: MouseButtonState::Up,
    ..
} = event { /* toggle window */ }
```

Rust-only, isolated. (Also removes an accidental double-toggle on left-click press+release.)

## #4 — Logs OFF by default but documented ON; failure paths unlogged

**Symptom:** No `skattr.log` in the data dir; testers can't produce logs.

**Root causes (two):**

1. `default_persist_logs()` returns **`false`** (`crates/core/src/daemon/config.rs:66`),
   but the comment at `crates/ui/src/main.rs:172` claims *"default ON during pre-1.0
   field-testing"* — **the comment is wrong**.
2. Even with logging enabled, the failure paths we care about **log nothing**: the
   frame-too-large rejection is swallowed (`peer.rs:543`), and the chunk-serve arm has no
   log statements. So logs wouldn't even reveal #1 or #2.

**Fix:** Correct the comment; add `warn!` lines to the silent send/serve failure paths.
**Decision needed:** whether to flip the default to ON for pre-1.0 field builds
(testability) vs. keep it OFF (privacy — a metadata-resistant messenger shouldn't leave
logs unless opted in). The default was NOT changed pending this decision.

**How to get logs today:** Settings → enable "Persist logs to disk" → **restart** → logs
appear at `%LOCALAPPDATA%\skattr\skattr.log` (`skattr_core=debug`).

## #5 — Close-to-tray toggle only applies after restart

**Symptom:** Changed "close to tray" in Settings, but [X] still went to the tray until
restart.

**Root cause:** The close handler reads a live `CloseToTraySentinel` atomic
(`crates/ui/src/main.rs:353-356`), which is *supposed* to be updated at runtime by the
frontend calling `set_close_to_tray` after each `SetConfig` (per the comment at
`main.rs:124-131`). But `patchConfig`
(`crates/ui/src-svelte/src/lib/stores/config.ts:63-107`) **never calls it** — the invoke
exists nowhere in the frontend. The Rust command is registered but dead. So the setting
only takes effect when the sentinel re-initializes from `config.toml` on next launch.

**Fix:** In `patchConfig`, after a successful `set_config`, if the patch includes
`close_to_tray`, `invoke("set_close_to_tray", { enabled })`. Frontend change (needs full
rebuild).

**Note:** the toggle *does* persist correctly to `config.toml`, so after one restart the
[X] button behaves as configured.

## Behavioral notes (not bugs, but surprising / worth documenting)

- **Received attachments are never auto-saved to a folder.** On completion the daemon
  keeps chunks encrypted-at-rest and only emits an availability event; the file is written
  only via explicit Open/Save (`peer.rs:148-186`; the guardrail even asserts "no plaintext
  written to download dir"). So a *successful* receive shows as a bubble with an Open/Save
  button, not a file appearing in Downloads. This contradicts the CLAUDE.md 3.B narrative
  ("reassembles to download_dir") — docs should be reconciled.
- **No sender-side delivery/progress status** (a deferred v1.1 item). This is *why* bug
  #1's failures are completely invisible on the sender.

## Build environment (resolved)

- The repo lives on **E: (exFAT)**, which cannot create symlinks → pnpm 10 install fails
  there.
- **Working local build:** frontend installs/builds on **C: (NTFS)**, built `build/`
  copied back to E:, then `cargo build -p skattr-ui` on E:. Verified →
  `target\debug\skattr-ui.exe`.
- Helper script: `build-ui-local.ps1` at repo root (`-RustOnly`, `-Run`, `-Release`).
  Recommend gitignoring it (machine-specific).
